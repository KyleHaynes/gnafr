gnafr

Flexible, transparent Australian address matching in R

Kyle Haynes

13 September 2026

The problem I needed to solve

I had large collections of Australian addresses that were almost right — and needed a repeatable way to connect them to an authoritative record.

Messy inputs

Abbreviations, spelling errors, missing punctuation, old street names, wrong postcodes and partial addresses.

Bulk work

Not an autocomplete box: hundreds of thousands of existing records processed together.

Explainable decisions

A single “confidence” number was not enough. I needed to see which parts agreed.

  • Use a real example: a legacy address with a typo and an old street name.
  • Batch linkage and auditability drive almost every design choice in the package.

There were useful pieces, but a workflow gap

Existing approach Useful for What I still needed
Hosted geocoding APIs Interactive lookup and managed infrastructure Local bulk processing without a per-request dependency
G-NAF import/manipulation tools Getting authoritative data into R Fuzzy matching, ranking and review as one pipeline
Parsers and autocomplete services Structuring text or finding suggestions Component scores and reproducible acceptance rules

The goal was not to claim there were no alternatives. It was to make a self-hosted, R-native, flexible matching workflow from input string to reviewable result.

Sources: Geoscape G-NAF metadata; gnaf.r; Addressr.

  • Say “limited fit”, not “nothing exists”. There are adjacent R tools and self-hosted services.
  • G-NAF is open data subject to the applicable licence, attribution and use restrictions.

gnafr in one sentence

A character vector goes in.

A scored, geocoded data.table comes out.

results <- gnaf_match(customer$address, con)

input → standardised input → matched G-NAF label → PID → coordinates → component scores

  • Uses the G-NAF data you choose to load
  • Runs matching in bulk inside DuckDB
  • Keeps unmatched inputs in the result
  • Returns the evidence needed to decide what “good enough” means
  • The interface is deliberately small: vector plus connection.
  • One input can return several candidates with max_results; unmatched rows are retained.

What it does — and what it does not

It does

  • Parse and standardise Australian address text
  • Search core, alias and custom address records
  • Score six address components
  • Return PIDs, labels, coordinates and relationships
  • Cache strong repeat matches
  • Support interactive review and threshold selection

It does not

  • Confirm that an address can receive mail
  • Turn the score into a probability of correctness
  • Guarantee a match when key evidence is absent
  • Hide uncertainty behind one opaque result
  • Replace domain-specific validation or labelled evaluation
  • “Matched to G-NAF” and “deliverable postal address” are different claims.
  • The package cannot know the cost of a false positive in the user’s project.

One engine, different definitions of success

Higher precision
Exact dwelling matters
Higher coverage
A usable location is enough
Control Towards precision Towards coverage
min_score Raise the acceptance bar Admit weaker candidates
max_results Review alternatives Return one best candidate
weights Emphasise number / flat Emphasise street / locality
aliases Inspect or restrict types Search all available aliases
street_only_fallback Usually off Match at street level when useful
principal / primary Resolve the entity needed Keep the label that best matched
  • There is no universal threshold. The cost of a false match determines the settings.

More than string matching

Build

gnaf_build_db() loads G-NAF Standard, aliases, indexes and street-level records.

Match

gnaf_match() parses, searches, scores, ranks and geocodes in bulk.

Extend

gnaf_add() brings internal or operational addresses into the same search.

Resolve

Principal, primary and alias fields distinguish a matched spelling from the dwelling or property.

Enrich

Saved geographies append SA2, LGA or other polygon attributes.

Review

Shiny and static diff views expose scores and generate filter code.

  • “Extend” covers PLI or service-address records that are valid internally but absent from G-NAF.

Give it the address you actually have

Best input

UNIT 2 16 WALLY STREET, NUNDAH QLD 4012

unit / levelstreet numberstreet name + typesuburbstatepostcode

Minimal preparation is better

  • Keep useful evidence: unit, building, street number, suburb, state and postcode
  • Remove fields that are not part of the address: customer IDs, names and notes
  • Do not spend time uppercasing, expanding Rd, or removing punctuation
  • Do not split into columns first unless the source is already structured
  • The parser handles case, punctuation and common abbreviations. Over-cleaning can discard evidence.
  • Better addresses are also faster: postcode, state and number make candidate retrieval cheaper.

Why DuckDB?

one file

con <- gnaf_connect("C:/data/gnaf.duckdb")
  • Persistent: build once, reuse across R sessions
  • Embedded: no database server to administer
  • Fast columnar scans, joins and window functions
  • SQL scores candidates before results enter R
  • Portable across machines and DuckDB clients

  • The national address table never needs to become an R object.
  • Keep one connection open across calls in an app or service.

Build once, use many times

  • Refresh when a new G-NAF release or internal-address extract matters.
  • A prepared file can be opened read-only by downstream users.

G-NAF Standard is distributed as PSV files through data.gov.au. Check the licence and use restrictions applying to your download.

  • Standard is preferred when aliases matter. gnaf_load() also accepts flattened G-NAF Core CSV.
  • Limit states when the project only needs specific jurisdictions.

Inside gnaf_match()

  • The key idea is progressive narrowing: cheap structure first, expensive string comparison later.
  • Street-only fallback is an optional final path omitted here for readability.

Step 1 — parse and standardise

address_parse("U 2, 16 wally st nundah qld 4012")
Raw evidence Parsed component Standardised value
U 2 flat type / number UNIT, 2
16 street number 16
wally st street name / type WALLY, STREET
nundah locality NUNDAH
qld 4012 state / postcode QLD, 4012

UNIT 2 16 WALLY STREET NUNDAH QLD 4012

  • Standardisation creates reliable join keys; it does not decide the match
  • Raw and standardised inputs both remain in the output
  • Parsing is deterministic preparation. Fuzzy similarity belongs in scoring.
  • A missing or misparsed number also widens candidate retrieval.

Step 2 — find plausible candidates

Candidate retrieval determines both speed and recall. A correct record removed here cannot be rescued by scoring.

  • Postcode and house number contribute score and prevent enormous comparisons.
  • Locality fallback is broader, so it only runs for the residue.

Step 3 — score agreement by component

Component Default weight
Street name 40
Postcode 20
Suburb 15
Street type / direction 10
Number / range / lot 10
Flat / level 5

Postcode20 / 20 Suburb15 / 15 Street name36 / 40 Street type10 / 10 Number10 / 10 Flat0 / 5 Total91 / 100

  • Similar text earns partial credit; conflicting or missing components lose credit
  • total_score is weighted agreement, not a calibrated probability
  • Custom weights must sum to 100
  • Read components before interpreting the total. Two 85s can describe different risks.
  • Calibrate on labelled examples from the intended population.

7.0 s 656.5 s 215.5 s 886.1 s

One measured run against a 13.9M-row database; hardware, database scope, alias volume and input quality materially affect timings.

  • This benchmark intentionally removes exact/cache wins and uses damaged addresses.
  • Repeated clean inputs can use exact-label and cache paths. Custom weights and max_results > 1 bypass the one-result cache.

Step 4 — return a useful audit table

results[, .(
  input_id, input_raw, input_standardised, matched,
  address_detail_pid, address_label, longitude, latitude,
  alias_type, total_score, score_street_name,
  score_number, match_rank
)]

For automation

Stable PID, coordinates, source, rank and selected geography columns.

For audit

Raw and standardised text, matched label, relationships and six component scores.

  • Unmatched inputs remain as rows, making joins to source data predictable.
  • max_results > 1 provides alternatives with deterministic ranks.

IVO Street: match, dwelling and property

Option Address fields describe Why use it?
default alias that won Explain exactly what matched
resolve_principal = TRUE alias + principal_* Compare both descriptions
return_principal = TRUE non-alias unit Link spellings to one dwelling
plus return_primary = TRUE parent property Aggregate units to a site

When address fields are replaced, matched_* preserves the alias that was scored. Score and rank always describe that original candidate.

  • Principal removes the alias; primary moves from a secondary/unit record to its parent property.

gnaf_threshold_filter()

  matched == TRUE &

]

Usage 2 — start simple, then expose choices

results <- gnaf_match(
  addresses, con,
  max_results = 1L,
  min_score = 80L,
  include_aliases = TRUE,
  include_custom = TRUE,
  return_principal = TRUE,
  street_only_fallback = FALSE,
  geographies = "sa2_2021"
)
If you need… Change…
alternatives for review max_results = 3L
a broad diagnostic population lower min_score, then filter
exact alias control set alias_types explicitly
parent-property output return_primary = TRUE
number-free street matches street_only_fallback = TRUE
repeat-run speed keep settings that permit cache = TRUE
  • Start with defaults and measure. Each option has a semantic or performance consequence.
  • include_aliases = FALSE cannot be combined with explicit alias_types.

A practical production pattern

# 1. Match broadly enough to study the distribution
candidates <- gnaf_match(
  source_dt$address, con,
  max_results = 3L,
  min_score = 60L,
  return_principal = TRUE
)

# 2. Review a labelled sample and choose explicit rules
gnaf_threshold_filter(candidates)

# 3. Apply the accepted rule and join by input_id
accepted <- candidates[
  match_rank == 1L &
  total_score >= 85L &
  score_street_name >= 30L
]
final <- accepted[source_dt[, source_row := .I],
                  on = .(input_id = source_row)]

Keep the full candidate table as an audit artefact. Filtered outputs are reproducible; discarded evidence is not.

  • Replace example thresholds with rules learned from a labelled sample.
  • Join on input_id; address strings may not be unique.

Three ideas to take away

1
Own the reference data

G-NAF and custom records live in a persistent, portable DuckDB file.

2
Keep judgement visible

Scores, alternatives and relationships explain the result.

3
Tune for the use case

Precision, coverage and output entity are explicit choices.
